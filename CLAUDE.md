# gonext (this repo)

This is the **gonext CLI tool's own codebase** — not a project generated by it. If you were dropped into `golden/` or a project scaffolded by `gonext init`, that tree has its own `CLAUDE.md`; this one is for working on the generator itself. See `README.md` for the product vision and `roadmap.md` for what's implemented vs. pending.

## Layout

| Path | What it is |
|---|---|
| `cmd/scaffold` | The `gonext init` CLI: prompts for a slug, copies `templates/`, runs `go mod init`/`tidy` + `pnpm install`, best-effort bootstraps Postgres. |
| `cmd/golden` | `make golden`'s implementation: regenerates `golden/` by shelling out to `gonext init golden-app ./golden`, backing up any existing `golden/` first. |
| `internal/scaffold` | Copy/substitution engine (`Copy`), destination resolution, slug validation/prompting — used by `cmd/scaffold`. |
| `internal/exec` | Thin `os/exec` wrapper for streamed, long-running subprocess steps (go mod tidy, pnpm install, docker compose). |
| `templates/` | The embedded source tree `gonext init` copies. **Not runnable as-is**: every internal Go import uses the literal token `[PROJECT-NAME]` instead of a real module path, and `go.mod`/`go.sum` are deliberately absent (regenerated fresh at scaffold time). Don't try to `go build` inside `templates/` directly. |
| `golden/` | A real, committed, runnable instance of `templates/` (slug `golden-app`) — real `go.mod`/`go.sum`, installed frontend deps. Edit code here to manually try out a feature idea before porting it into `templates/`. |

## Where does a new feature's code go?

Ask whether the feature becomes part of every generated project's own source tree, or is a capability of the `gonext` tool itself:

- **Scaffoldable** — code, config, or Makefile targets that should be copied verbatim into generated projects by `scaffold.Copy()` — goes in `templates/`. The name says it all.
- **CLI-native** — a capability a generated project invokes but does not vendor, such as a `gonext dev` live-reload subcommand — goes in this repo's `cmd/` (as a new subcommand) and `internal/` (its implementation). Running it from inside any scaffolded project always executes whatever `gonext` is currently installed, never a copy frozen at scaffold time.
- **Core library** — a small, stable type or interface that generated projects *and* third-party extensions both compile against — goes in a top-level package of this same module (today `auth/`, imported as `github.com/dennys-bd/gonext/auth`). gonext ships as **one module under one version**: the CLI a developer runs and the library their project imports are the same artifact at the same `vX.Y.Z`. Use this only when an implementation has to be writable from outside a generated project — a port scaffolded into `<project>/backend/internal/…` gives every project a distinct type at an `internal`-sealed path, so nobody can implement it externally. The bar is deliberately high: a port with at least two plausible implementations, one of which someone outside this repo might write. Such a package must import **stdlib only**, so a project taking gonext as a dependency compiles none of the CLI's charmbracelet tree.

## The templates/ ↔ golden/ relationship

`golden/` exists to solve one problem: `templates/` can't be run directly, so there needs to be a real, editable, always-working instance to test against. It is regenerated with:

```sh
make golden
```

which is `go run ./cmd/golden` — it backs up any existing `golden/` to `golden-old/` first (or prompts if `golden-old/` is already occupied), then runs `go run ./cmd/scaffold init golden-app ./golden`.

**Workflow when changing `templates/`:**
1. Prototype and manually verify the change directly under `golden/backend/` or `golden/frontend/` (`go run ./golden/backend/cmd/server`, `pnpm dev` in `golden/frontend`, etc.).
2. Once it works, hand-port the change into the matching file(s) under `templates/`, restoring the `[PROJECT-NAME]` token wherever the concrete `golden-app` module path appears in Go imports.
3. Run `make golden` to regenerate `golden/` from `templates/` — this discards any leftover experimental code not yet ported and resets `golden/` to exactly match the template.

**The drift guarantee**: `cmd/scaffold/copy_golden_test.go` (`TestCopy_GoldenSnapshot`) runs `scaffold.Copy()` against the real embedded `templates/` and diffs the output byte-for-byte against `golden/`. If `templates/` changes without regenerating `golden/` (or vice versa), this test fails. It excludes only what `Copy()` never writes: `go.mod`, `go.sum`, `.env`, and the tool-generated `frontend/node_modules/`, `frontend/.next/`, `backend/bin/` — everything else must match exactly.

**Never hand-edit `golden/` and expect it to persist** — any change not also made in `templates/` is silently discarded by the next `make golden`, and any change made in `golden/` alone (without a matching `templates/` edit) will fail the drift test.

## Working in golden/ without polluting the fixture

`golden/` is a real working directory *and* a byte-for-byte test fixture at the same time. Running dev tooling inside it (`pnpm typecheck`, `tsc`, a local build, `cd`-ing into it and letting hooks write state there) leaves real files on disk that `TestCopy_GoldenSnapshot` will flag as unexpected, even when they're gitignored. Before committing a `golden/` regeneration, check `git status --short golden/` for anything unexpected, and `go test ./cmd/scaffold/...` should be green.

## Tests

Standard `go test`, table-driven, with `-race` in CI-equivalent runs:

```sh
go build ./auth/... ./cmd/... ./internal/... .   # excludes templates/, which never builds standalone
go vet ./auth/... ./cmd/... ./internal/... .
go test -race ./auth/... ./cmd/... ./internal/... .
```

`make test` runs exactly that. There is one module, so no separate invocation is needed for `auth/`.

`cmd/scaffold/init_e2e_test.go` is opt-in only (`GONEXT_E2E=1`) since it hits the network and installs real dependencies into a temp dir — it's not part of the fast loop.
